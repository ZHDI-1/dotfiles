# 技术问题分析文档

默认读者懂相关系统的基础，但没有参与这次排查。他们打开文档时想先知道：发生了什么、为什么、有多确定、接下来怎么办，然后再决定要读多少证据。这个 Skill 的工作是让文档按这个顺序回答，并让每个结论的强度与证据相称。用户指定了其他读者时，调整背景深度和术语，判断标准不变。

## 适用边界

适用于核心内容是对一个或一组具体技术问题做因果论证或状态判断、且用户要写、改或审这份文档的情况。

以下情况不套用本 Skill 的结构和评审机制：

- 排查本身（读 core、看日志、定位代码）。排查告一段落、需要成文时再使用。
- 解释代码或机制，读者的目标是理解系统而不是理解一次问题。
- 设计文档、方案、API 文档、周报。
- 事故报告中的影响统计、响应过程、沟通和改进项跟踪。混合文档只对技术因果部分使用本 Skill，其余按团队惯例。

用户只要求润色或改错字时，只做语言层修改，不调整结构和结论强度。若发现会误导技术结论的问题，在修改结果之外单独列出，由作者决定。

## 确定模式和类型

看用户期待的产出来判断模式：

- 新写：手头是排查记录、日志、聊天记录或零散笔记，需要成文。
- 重构：已有成文文档，要整理结构、精简、拆分，或把 WIP 收束为终稿。
- 评审：要意见、挑问题、判断能否定稿。

仍不清楚时问一句“想要改好的文档，还是先要意见”。

类型决定结构。按读者的主要问题判断：

| 类型 | 读者的主要问题 |
|---|---|
| 故障复盘 | 发生了什么、影响多大、为什么、修好没有、会不会再来 |
| 确定性根因分析 | 精确机制是什么，凭什么确定 |
| 调查中（WIP） | 现在知道什么、排除了什么、下一步查什么 |
| 现场状态分析 | 系统此刻处于什么状态，能直接推出什么 |
| 多 case 汇总 | 这些 case 是否同一问题，各自证据到哪一步 |

混合文档按主要问题选主类型，其余部分作为章节遵循各自类型的要求。确定类型后读 [references/doc-types.md](references/doc-types.md) 中对应小节。

## 核心原则

每条原则对应一种会让读者误判或读不下去的情况。细则和改前改后示例见 [references/evidence-rules.md](references/evidence-rules.md)。

1. **状态先于细节。** 开头几行交代结论状态（已确认、高置信推断、候选、调查中、仅现场描述）、一句话结论或当前最可能解释、影响范围、可能推翻结论的未知项。WIP 和现场文档没有结论，但有状态。
2. **事实、推断、假设、未知分开。** 事实带来源；推断写出依赖哪些事实；假设写出什么证据能证实或否定它；未知写明是否影响结论。不必逐句贴标签，在混淆会改变判断的地方显式区分。
3. **结论强度与证据相称。** 指标相关、时间先后都不足以称为主因，还需要机制、对替代解释的排除，以及本次确实发生的证据——现场直接证据或干预结果其一即可。证据不够时降低措辞，而不是补一个看起来合理的故事。
4. **一个结论只有一个主要证明位置。** 摘要、时序、修复等章节可以一句话复述并引用，不再重新证明。重复证明会让同一份证据看起来像多份独立佐证，修订时也容易改出前后不一致。
5. **每段回答读者此刻的一个新疑问。** 主阅读路径围绕读者当前要做的判断组织。背景在第一次需要时给到够用为止，排查过程记录和完整机制说明移到附录。
6. **跨时刻、跨对象、跨版本的证据显式标注。** 放在一起推理时写明差异和可以合并的理由。为说明“可能发生”而构造的时序，要标为构造时序，并区分其中哪些步骤有观测证据。
7. **因果链落到可观测结果。** 最后一跳对应读者能看到的现象，并说明触发条件：为什么是这次、这个节点、这个时间。
8. **复现说明证明范围。** 写清复现条件、对应线上哪个现象、证明了什么、没有证明什么。
9. **修复对应失效前提。** 说明修复恢复了哪个前提或切断了因果链的哪一跳，是根治还是规避，验证覆盖到哪里。
10. **图、日志、代码先说明证明什么，再展示。** 裁剪到相关部分，保留原始时间戳和标识符，省略处标出。
11. **素材分层而不丢失。** 完整日志、推理过程、机制说明可以移到附录，不因追求简短而删掉。排除替代解释是证明的一部分，主文保留一句话结论。
12. **结构服务于类型。** 不设固定章节和字数；没有内容的章节不写，状态块可以只有两行。团队已有的标签和章节名能表达同样的区分时沿用。
13. **不编造证据。** 缺少的时间戳、数值、版本、日志用 `[待补充：…]` 标出，不用合理推测填空。

文档语言：正文用中文；函数名、字段、配置项、日志关键字、命令保留英文原文并使用代码格式；日志和报错不翻译；同一概念全文用同一个术语。

## 新写

1. 读完全部素材，判断类型和结论状态。只有当类型或状态会改变结构、素材又无法判断时才问用户；其他缺口先在草稿中标出。
2. 起草前列出结论清单：每个结论的证据、强度，以及证据的时刻、对象、版本。这份清单用于组织，不必交给用户。
3. 按类型排定读者的问题顺序，为每个结论选定唯一的主要证明位置。
4. 先写状态块，再写主阅读路径，最后把剩余素材放进附录。新写时只收录支撑论证或排除的素材，大段原始数据注明存放位置。
5. 用 [references/review.md](references/review.md) 的“常见必须修改项”自检一遍，修正后交付。自检只针对必须修改项，不反复打磨措辞。

交付时附简短说明：选择的类型、结论状态的依据、所有 `[待补充]` 缺口。

## 重构

重构改变结构和表达，不改变技术内容。开始前读 [references/restructure.md](references/restructure.md)。要点：

- 先盘点结论、证明位置、证据、背景、推理记录、机制说明，再动结构。
- 日志、代码、数值、时间戳、标识符原样保留。
- 每段原有素材都有去向：留在主文、移到附录，或作为完全重复被合并并注明重复位置。
- 发现过度表述、前后矛盾时单独列出。直接降级措辞的，逐条写明原句、改后和原因；涉及结论状态、主要因果链或文档类型的改动，先征求作者意见。

## 评审

评审回答的核心问题是：这份文档会不会让读者在技术判断上出错。意见分两级：

- **必须修改**：不改的话，认真但未参与排查的读者会在“发生了什么、为什么、有多确定、修复是否有效、影响范围”中至少一项得出错误判断，或者文档在影响上述判断的事实、数值或机制上自相矛盾。每条写明误导的是哪个判断，并给出可关闭的修改方式：补证据，或把表述降级到现有证据能支撑的程度。
- **可选改进**：其余所有意见，包括重复、顺序、篇幅、措辞、格式。按收益排序，只列最值得的几条，标明可不改。

重复、结构不佳、背景过长本身属于可选改进；只有当它们造成上述误判时才升级为必须修改。常见必须修改项和输出格式见 [references/review.md](references/review.md)。

只拿到文档、没有原始材料时，在结论中说明评审只覆盖内部一致性和结论与证据的匹配，未核对原始数据。

### 停止条件

- 必须修改项全部关闭，即给出“可以定稿”。可选项不阻塞定稿，也不作为下一轮评审的依据。
- 复审以上轮评审输出为输入；拿不到时请用户提供，否则说明按首轮评审处理。
- 复审只检查上轮必须修改项是否关闭，以及本轮改动处是否引入新的必须修改问题，不对未改动的文字提新的可选意见。
- 复审只为核对改动读必要的上下文，不重新通读。由此发现的上轮遗漏，只有会使读者误判结论状态、主因或修复有效性时才提出并注明“上轮遗漏”，其余不再提出。
- 因缺少证据无法补齐的项，结论降级并列入未知后即视为关闭，不要求作者继续排查。
- 作者明确不接受的必须修改项，记录一次分歧及其可能导致的误判，后续轮次不再重复；已记录的分歧不阻塞定稿。
- 剩余意见只涉及措辞时，直接说明可以定稿。
