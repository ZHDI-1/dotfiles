# 文档类型与结构选项

各类型读者的主要问题见 SKILL.md 的类型表。这里给出开头写法、常见结构和收束方式。结构是示例，按素材裁剪，没有内容的部分不写。

目录：状态块｜故障复盘｜确定性根因分析｜调查中（WIP）｜现场状态分析｜多 case 汇总｜混合文档与类型迁移

## 状态块

开头几行回答：结论状态、一句话结论或当前最可能解释、影响范围、可能推翻结论的未知。状态用词及其依据见 evidence-rules.md 的“结论状态”。以下两例只示意写法，行数和字段按需增减。

> 状态：根因已确认（vmcore 中对象状态与代码路径逐跳对应，未做复现）；受影响的版本范围仍在核实。
> 结论：客户端重连时没有作废旧会话上的 in-flight 请求，旧请求的完成回调在新会话上执行，导致对象引用计数提前归零。
> 影响：开启该特性的客户端在服务端重启期间可能触发；本次 3 个节点出现。
> 未确认：更早版本是否同样受影响。不影响机制结论，影响升级范围。

> 状态：调查中（第 3 次更新，YYYY-MM-DD）
> 当前最可能解释：H1 锁等待被重试放大（依据见 §2）；已排除：H3 磁盘慢；仍开放：H2。
> 下一步：采集 X；若 X 显示……，方向转向 H2。

## 故障复盘

常见顺序：状态块 → 现象与影响 → 根因或当前结论（主要证明位置）→ 触发条件 → 修复与验证 → 残留风险与未知 → 附录。

- 现象只写读者可以核对的观测：报错、指标、时间窗口、范围，与解释分开。
- 主文时间线只保留与因果相关的节点，每个时间点注明来自哪个对象、哪类来源；完整时间线放附录。
- 响应过程、沟通、改进项跟踪可以存在，但不和技术因果混写；响应时间线被当作证据时，同样遵守时刻和对象标注。
- 根因未确认时，按 WIP 的方式写状态和开放问题，不为了复盘格式完整而写出一个“根因”。

## 确定性根因分析

完整闭环通常是：现场证据 → 代码路径或状态机 → 被违反的前提或不变量 → 触发条件 → 复现 → 修复 → 验证。每一环只出现一次，后面的环节用名称引用前面的内容（如“前提 P1”），不重新讲机制。

- 给失效前提命名，修复章节直接对应它。
- 时序图或交错表只放在一处，用来证明竞争窗口存在。
- 代码证据注明对应的运行版本；读的是主线代码而线上是旧版本时，说明差异是否影响结论。
- 回答为什么以前没有触发、这次为什么触发。

## 调查中（WIP）

常见组织：状态块 → 已确认事实 → 假设（各自的支持证据、反对证据、验证方法）→ 已排除及依据 → 未知 → 下一步及判定标准。

- WIP 的主要价值是区分初步推断、疑点和未知。后续更新中，推断升级为事实要有新证据并写明，不能因为反复出现就默认成立。
- 每次更新改写开头的状态块，写明现在相信什么、相比上次变了什么、下一步及不同结果分别意味着什么；不在末尾另写收束。
- 更新时改写正文，而不是只在末尾追加；旧推理移入“调查记录”附录。
- 调查结束要收束。定位成功时转为根因分析或复盘（见“类型迁移”）；停止调查时写明停止原因、最可能的解释及其证据等级、残留风险、重新打开的条件。

## 现场状态分析

常见组织：现场来源（时间、对象、获取方式、多份现场是否同一时刻）→ 关键状态（谁持有什么、谁在等什么、各对象处于状态机哪一步）→ 直接推论 → 现场无法推出的内容 → 建议的下一步取证。

- 现场文档的价值在于准确。根因方向可以作为假设写出并说明需要什么证据，但不写成结论。现场状态与代码路径已逐跳闭合时，按“类型迁移”转为根因分析。
- 引用原始字段名和值，让读者能回到现场核对。
- 多份现场（多个 core、多次 dump）分别标注时刻和对象，合并推理时说明依据。

## 多 case 汇总

适合用表格：每行一个 case，列出现象、关键证据、证据等级、归因、与其他 case 的关系。表格前写清归类标准；无法归类的 case 单列，不硬归。

- 区分“同根因”和“同症状”。症状相似只支持“可能同源”；归为同根因需要每个 case 自己的证据。
- 整体结论的强度不超过关键环节中最弱的一环；证据充分的 case 不能替证据不足的 case 背书。
- 单个 case 的详细分析放附录或各自文档，主文只放比较和结论。

## 混合文档与类型迁移

- 混合文档按读者的主要问题选主类型。例如“复盘 + 精确根因”以复盘为主，根因章节内部遵循根因分析的闭环。
- WIP 转为根因已确认：重写状态块和结论，确定唯一的主要证明位置，被排除的假设汇总为一节，调查过程移入附录。只在末尾追加“最终结论”是不够的，前文的初步推断仍会被当作有效内容读到。
- 现场分析发展为根因分析：现场章节保留为证据来源，新增因果链和复现，现场章节不再承担推测。
- 多 case 中某个 case 定位后：更新该行的证据等级，并检查其他 case 的归类是否仍然成立。
