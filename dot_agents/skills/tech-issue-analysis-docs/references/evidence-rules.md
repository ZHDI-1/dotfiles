# 证据与结论规则

## 结论状态

以下是建议用词。团队已有用词时沿用，但保持同样的区分。

| 状态 | 通常需要的依据 |
|---|---|
| 已确认 | 因果链每一跳都有本次发生的证据：现场直接证据（core、内存中的对象与锁状态、日志、trace），或由已观测状态经与运行版本一致的代码路径必然推出；能解释全部关键现象，或列出未解释项；主要替代解释已排除 |
| 高置信推断 | 能解释全部关键现象，替代解释已排除，但某一跳缺少直接证据（写明是哪一跳） |
| 候选 / 部分解释 | 只能解释部分现象，或仍有未排除的竞争解释 |
| 调查中 | 还没有主要解释 |
| 仅现场描述 | 只陈述状态，不做因果主张 |

写“已确认”之前，先回答三个问题：本次确实走了这条路径的证据是什么；还有哪些关键现象没有解释；排除了哪些替代解释。答不上来的部分写进文档，并考虑降一级。

复现、修复验证、回滚是干预证据：现场证据只到相关或时序时，它们是升级为已确认的主要途径；现场证据已逐跳闭合时不是前提，缺少它们只影响复发概率、修复有效性等结论。

## 四类陈述与措辞

- 事实：直接观测，带来源。“节点 B 的日志在 10:02:15 出现 `heartbeat timeout`。”
- 推断：由事实推出，写出依赖。“由于……且……，推断……。”
- 假设：尚未证实，写出检验方法。“若 H2 成立，应能在……中看到……。”
- 未知：写明影响。“……尚不清楚；不影响机制结论，但影响范围判断。”

同一结论在全文使用同一档措辞，并与状态一致：

| 状态 | 常用措辞 |
|---|---|
| 已确认 | 是、导致、根因为 |
| 高置信推断 | 基本可以确定、很可能（同时写明缺哪一跳的直接证据） |
| 候选 | 可能、怀疑、倾向于 |
| 未知 | 尚不清楚、未确认 |

一个与证据等级匹配的限定词就够，避免“可能大概率疑似”式的叠加；推断前不用“显然”“毫无疑问”。无争议的背景事实照常陈述，不必标注。

## 时刻、对象、版本

两条证据一起支撑某个推断时，检查它们是否来自同一时刻、同一对象（节点、进程、连接、请求、文件……）、同一软件版本。任何一项不同，就在推断旁写明，并说明为什么仍可合并：状态在这段时间内不变、对象等价、行为与版本无关等。读者默认并列的证据描述同一时刻和同一对象，不标注就会被误读。

- 跨节点按时间戳排序时，确认时钟误差小于需要区分的间隔；不确定时写明顺序依赖这一假设。
- 聚合指标（分钟级平均、采样数据）不能支撑比其粒度更细的时序结论。

> 图 2 的 core 显示请求卡在等锁，日志显示持锁线程正在重连，所以是重连持锁导致请求卡住。

改后：

## 从相关到主因

把某个因素称为主因之前，看证据走到哪一级：

1. 相关：该因素与症状同时出现或共同变化。
2. 时序：该因素的变化先于症状。
3. 机制：有代码或原理支撑的路径，从该因素通向观测到的症状。
4. 排除：主要替代解释已被检查并排除，且列出了是哪些。
5. 发生或干预：本次现场有该路径逐跳发生的直接证据，或改变该因素后症状随之改变（复现、修复、回滚、限流、切换配置）。

只到 1–2 级时写“相关因素”或“候选原因”；3–4 级可以写高置信推断；有第 5 级证据才适合写已确认。多个因素共同作用时，说明各自是必要条件、触发条件还是放大因素，不把“必要条件之一”写成主因。

改前：

> 故障期间 CPU 使用率升至 95%，延迟同步升高，CPU 瓶颈是延迟升高的主因。

改后：

> 故障期间 CPU 使用率升至 95%，与延迟升高出现在同一分钟（相关；分钟级指标无法区分先后）。CPU 升高是原因还是重试放大的结果尚未确认，区分两者需要……。在此之前，CPU 只列为候选因素。

## 因果链与触发条件

因果链写成可以逐跳核对的形式，每一跳注明证据或标为推断，最后一跳落到读者能观测到的现象。读者无法把链条终点与开头描述的现象对上时，链条就没有完成。

根因解释还要回答触发条件：为什么以前没发生，为什么是这次、这个节点、这个时间。缺少触发条件的解释通常只说明了“能发生”，没说明“这次为什么发生”。现场已直接证明机制发生、但触发条件查不清时，列入未知并写明影响，不因此降级机制结论。

## 构造时序

为说明某种交错“可能发生”而构造的时序，与从日志、trace 中还原的实际时序作用不同。构造时序需要：

- 在标题或首句标明是构造时序，以及它要证明什么（通常是竞争窗口存在，且该交错能产生观测到的现象）；
- 区分每一步是有观测证据、是推断，还是为构造而假设；
- 指出它与实际观测在哪里吻合、哪里没有证据。

把构造时序放在“时间线”一类标题下而不加说明，读者会把它当作线上真实路径。

## 复现的证明范围

复现说明包括：

- 条件：版本、配置、注入的故障或延迟、放大触发概率的手段；
- 结果：观测到什么，与线上哪个现象对应，哪些不对应；
- 证明了什么：通常是该机制能够产生该现象；
- 没有证明什么：通常是线上确实走了这条路径、线上触发概率、是否存在其他路径。

注入延迟复现竞争，说明窗口存在，不说明线上窗口同样大。复现失败也是证据，写明尝试了哪些条件。

## 修复与失效前提

修复对应到具体的失效前提或因果链中的某一跳：恢复了哪个前提（如“执行回调前确认会话代数一致”），或切断了哪一跳。同时说明：

- 根治还是规避、止血；
- 可能的副作用和覆盖不到的路径；
- 验证方式和范围：复现是否不再触发、测试覆盖了哪些交错、线上观察了多久，以及这些验证不能排除什么。

低频问题“修复后未复发”是弱证据，写明观察时长与原先的发生频率。根因未确认时，修复对应的是假设中的前提，要写明这一点；修复效果只能支持该假设，不能单独证实它。修复章节引用前提名称即可，不重讲因果链。

## 图、日志、代码

每个图、日志片段、代码片段之前，用一句话说明它证明什么。读者看完片段应能回到这句话核对。

- 日志：保留原始时间戳、对象标识和关键字段，裁掉无关行，省略处用 `...` 标出；多来源的日志注明来源。
- 代码：注明版本或提交、文件和函数名，只保留与论证相关的行，在正文中点出关键行；完整函数可放附录。
- 图：标明数据来源、时间范围和粒度；示意图与实测数据图要能一眼区分。

一段素材说不出证明作用，通常意味着它属于附录。

## 主要证明位置与引用

每个结论选一个主要证明位置，其他地方用一句话复述并引用（如“机制见 §3.2”），引用用章节编号或标题，方便跳转。同一份证据在多处出现时，说明是同一份，避免读者以为有多份独立佐证。摘要、时序、修复三处最容易重复证明，写到这些地方时先检查是否又在重讲。

## 主阅读路径与附录

主阅读路径只包含读者接受结论或做出当前判断所需的内容。判断一段是否留在主文：去掉它之后，读者会不会对结论或其确定程度产生疑问。

- 背景知识在第一次需要的地方给最少够用的解释；完整机制说明放附录或单独成文并引用。
- 排查过程（包括走过的弯路）放附录“调查记录”。它有学习价值，但不在证明路径上。
- 被排除的假设：主文保留“排除了什么、凭什么”的一句话，细节放附录。
- 附录按类型组织（原始日志、完整时间线、调查记录、机制说明、被排除的假设），并从主文引用。

## 模型与简化的局限

用简化模型论证时（状态机抽象、排队模型、简化时序），写明省略了什么，以及省略是否可能影响结论。读者由此知道结论在什么范围内成立，什么条件下需要重新审视。
